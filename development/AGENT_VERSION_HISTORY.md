# V8 — Goal Execution

**핵심 문제**

초기 RAG는 질문을 받으면 관련 문서를 검색하고 답변을 생성하는 형태에 가까웠다.  
하지만 실제 연구 작업은 검색 한 번으로 끝나지 않고, 검색 → 계산 → 검증처럼 여러 단계가 필요하다.

**수정 방향**

Agent에 목표(Goal)와 실행 상태(State)를 두고, 매 반복마다 다음 행동을 선택하도록 구성하였다.

```
User Query
→ Goal Setup
→ Select Next Action
→ Retrieve / Calculate
→ Verify
→ Check Goal Completion
→ 반복 또는 Final Answer
```

**쉽게 말하면**

기존에는 “질문 → 답변”이었다면, V8부터는 “해야 할 일을 정함 → 필요한 작업을 순서대로 함 → 끝났는지 확인” 구조가 시작되었다.

**논문 표현 예시**

> 단일 질의응답 방식에서 벗어나 연구 목표를 기준으로 검색, 계산 및 검증 단계를 반복 수행하는 목표 지향형 실행 구조를 도입하였다.

---

# V9 — 계산 근거와 전제 검증 강화

**핵심 문제**

계산 자체가 맞더라도 사용한 값이나 관계식의 출처가 불명확할 수 있고, 사용자의 질문에 잘못된 전제가 포함될 수 있었다.

**수정 방향**

- 계산 결과의 provenance(출처)를 추적
- 관계식과 입력값이 어디에서 왔는지 확인
- 질문의 전제가 내부 문헌과 충돌하는지 검사

**쉽게 말하면**

“숫자만 맞으면 됨”이 아니라 “이 숫자를 왜 썼고 이 공식이 어디에서 왔는지도 확인”하게 만들었다.

**논문 표현 예시**

> 계산 결과의 신뢰성을 확보하기 위해 입력값과 관계식의 출처를 추적하고, 질의에 포함된 전제를 내부 문헌과 비교하여 검증하는 기능을 추가하였다.

---

# V10 — 행동 선택과 Grounded Execution 개선

**핵심 문제**

질문에 따라 검색이 필요한지, 바로 계산해야 하는지, 추가 검증이 필요한지가 다르지만 잘못된 행동을 선택하는 경우가 있었다.

**수정 방향**

질문의 목적과 현재 확보된 정보에 따라 Retrieve, Calculate, Verify 등의 실행 경로를 더 명확하게 선택하도록 라우팅을 개선하였다.

**쉽게 말하면**

“계산만 하면 되는 질문인데 괜히 검색”하거나 “공식을 찾아야 하는데 바로 계산”하는 문제를 줄이는 단계였다.

**논문 표현 예시**

> 질의 유형과 확보된 근거 상태에 따라 검색, 계산 및 검증 도구를 선택하는 실행 라우팅을 개선하였다.

---

# V11 — 사용자 입력값 파싱 개선

**핵심 문제**

`SG=0.918`, `phi=0.2`, `압력은 2500 psi`처럼 같은 정보를 다양한 방식으로 입력하면 숫자와 변수의 의미를 잘못 읽는 경우가 있었다.

**수정 방향**

- 사용자 숫자 입력 추출
- 변수명과 값 연결
- 계산 요청 여부 판별
- 단순 계산 fast path 보강

**쉽게 말하면**

사용자가 준 숫자가 “무슨 값인지” 더 정확히 읽도록 고쳤다.

**논문 표현 예시**

> 자연어와 기호가 혼합된 사용자 입력으로부터 수치, 변수 및 단위를 구조화하여 계산 단계에서 활용할 수 있도록 입력 파싱 기능을 개선하였다.

---

# V11.1 — 전제 Grounding과 석유공학 검색 강화

**핵심 문제**

잘못된 기술적 전제를 가진 질문이나 석유공학 전문 용어가 포함된 질문에서 일반적인 검색어만 사용하면 원하는 근거를 찾지 못할 수 있었다.

**수정 방향**

- premise grounding 강화
- 석유공학 도메인 용어를 이용한 검색어 확장
- 관련 문헌을 찾은 뒤 전제를 교정할 수 있도록 개선

**논문 표현 예시**

> 석유공학 도메인 용어를 반영한 검색어 확장과 전제 검증을 적용하여 전문 질의에 대한 근거 검색 정확도를 개선하였다.

---

# V12 — 공식 선택과 변수 Binding

**핵심 문제**

문헌에 공식이 있어도 사용자 입력의 `phi`, `Rw`, `Sw` 등이 공식의 변수와 정확히 연결되지 않으면 계산을 진행할 수 없었다.

**수정 방향**

- 공식 후보 선택
- RHS 변수 분석
- 사용자 값과 공식 변수 연결(binding)
- 단위 및 누락 변수 검사

**쉽게 말하면**

“교재 공식의 빈칸에 사용자가 준 값을 정확히 넣는 과정”을 체계화한 버전이다.

**논문 표현 예시**

> 문헌에서 추출한 관계식의 입력 변수를 사용자 제공 값과 연결하는 변수 바인딩 절차를 구축하고, 누락 변수 및 단위 적합성을 검증하였다.

---

# V15 — 원래 사용자 입력 보존

**핵심 문제**

여러 단계를 거치면서 원래 사용자가 제공한 값이나 operand가 변환 과정에서 누락되거나 다른 의미로 해석될 가능성이 있었다.

**수정 방향**

계산 계획을 생성하거나 근거를 추가한 뒤에도 최초 사용자 입력을 canonical fact로 유지하도록 개선하였다.

**쉽게 말하면**

처음 받은 숫자를 중간 과정에서 잃어버리지 않게 만들었다.

**논문 표현 예시**

> 다단계 실행 과정에서도 최초 사용자 입력을 추적 가능한 사실 객체로 유지하여 계산 입력의 일관성을 확보하였다.

---

# V16 — 근거가 충분하면 계산까지 연결

**핵심 문제**

검색으로 올바른 공식과 값을 찾았는데도 “근거 확인” 단계에서 멈추고 실제 계산으로 넘어가지 못하는 경우가 있었다.

**수정 방향**

answerability와 calculation readiness를 분리하고, 공식과 입력이 검증되면 계산 단계로 전환하도록 개선하였다.

**쉽게 말하면**

“공식까지 찾았는데 계산은 안 함” 문제를 줄인 버전이다.

**논문 표현 예시**

> 검색된 관계식과 입력값이 실행 조건을 충족하는 경우 검증 단계에서 계산 단계로 자동 전환하도록 실행 조건을 개선하였다.

---

# V17 — 한글·영문 질의 Grounding 개선

**핵심 문제**

같은 의미라도 한글과 영어 표현이 다르면 검색 근거나 계산 입력 연결 결과가 달라지는 문제가 있었다.

**수정 방향**

한글/영문 표현에서도 동일한 engineering concept와 사용자 입력이 유지되도록 grounding과 입력 보존을 강화하였다.

**논문 표현 예시**

> 한글 및 영문 질의 간 표현 차이가 검색 및 계산 입력 연결에 미치는 영향을 줄이기 위해 다국어 의미 매칭을 보강하였다.

---

# V18 — 실행 과정 가시화

**핵심 문제**

Agent가 여러 번 검색·계산·검증을 반복하면 사용자는 현재 무엇을 하고 있는지 알기 어려웠다.

**수정 방향**

Goal Research의 iteration과 완료 상태를 UI에서 더 명확하게 보여주도록 정리하였다.

**쉽게 말하면**

Agent 머릿속의 “작업 순서”를 화면에서 보기 쉽게 만든 단계다.

**논문 표현 예시**

> 사용자가 에이전트의 진행 상태와 실행 결과를 확인할 수 있도록 반복 실행 과정과 목표 완료 상태를 인터페이스에 시각화하였다.

# V19 — 사용 화면 단순화

**핵심 문제**

개발 과정에서 옵션과 설정이 많아져 실제 사용자에게는 복잡한 화면이 되었다.

**수정 방향**

Goal Research 설정 영역을 단순화하고 사용자가 질문과 결과에 집중할 수 있도록 UI를 정리하였다.

**논문 표현 예시**

> 실제 사용성을 고려하여 에이전트 설정 요소를 단순화하고 질의 및 결과 중심의 인터페이스로 개선하였다.

# V20 — Unified Autonomous Chat

**핵심 문제**

일반 채팅과 Agent 실행이 분리되어 있으면 사용자가 어떤 모드를 사용해야 하는지 판단해야 했다.

**수정 방향**

하나의 채팅 인터페이스에서 질의를 분석하고 필요한 경우 자율적으로 검색·계산·검증을 실행하도록 통합하였다.

**쉽게 말하면**

사용자가 “이건 RAG 버튼, 이건 계산 버튼”을 고르는 대신 그냥 질문하면 Agent가 알아서 결정하게 만든 단계다.

**논문 표현 예시**

> 질의응답과 도구 실행을 하나의 대화 인터페이스에 통합하여 사용자가 별도의 실행 모드를 선택하지 않아도 작업 유형에 따라 필요한 도구를 자동 선택하도록 구성하였다.

# V20.1 — 통합 시스템 안정화

**핵심 문제**

V20에서 기능을 한 화면으로 합친 뒤 브라우저와 실행 흐름의 안정성을 추가로 확인할 필요가 있었다.

**수정 방향**

브라우저 E2E 및 reliability 테스트를 통해 통합 이후 발생하는 실행 오류를 보완하였다.

**논문 표현 예시**

> 통합 인터페이스 도입 이후 브라우저 기반 실행 검증과 회귀 테스트를 수행하여 시스템 안정성을 보완하였다.

# V21 — 일반화(Generalization)

**핵심 문제**

개발 테스트 문장에서는 잘 동작하지만 표현을 조금 바꾸면 의도를 놓치는 문제가 남아 있었다.

**수정 방향**

특정 문장 문자열이 아니라 의미와 작업 유형을 기준으로 판단하도록 일반화하였다.

**쉽게 말하면**

“합계 계산해줘”만 알아듣는 것이 아니라 “전부 더하면?”, “총 생산량?”, “combined rate?”도 같은 작업으로 이해하도록 만드는 단계다.

**논문 표현 예시**

> 특정 질의 문구에 의존하지 않도록 의미 기반 의도 분류와 작업 유형 일반화를 적용하였다.

# V21.1 — 의미 기반 근거 검증과 공식 Binding 보강

**핵심 문제**

관련 단어가 포함되었다는 이유만으로 실제 주장을 뒷받침하지 않는 문장을 근거로 사용할 수 있었고, 공식의 변수가 유사한 이름 때문에 잘못 연결될 가능성이 있었다.

**수정 방향**

- citation semantic support 강화
- source-local 의미 확인
- formula variable binding 보강

**논문 표현 예시**

> 단순 키워드 일치가 아닌 의미 수준의 근거 지지 여부를 확인하고, 관계식 변수의 의미와 출처 문맥을 고려하여 입력값 연결 정확도를 향상시켰다.

# V21.2 — Goal Completeness

**핵심 문제**

질문에 여러 요구사항이 있어도 일부만 완료한 뒤 전체 작업이 끝난 것으로 판단할 수 있었다.

**수정 방향**

Required Goal을 고정하고 모든 필수 목표가 충족되었는지 확인하도록 개선하였다.

**평가에서 확인된 한계**

V21.2의 최종 unseen V3에서는 Hallucination-free 특성은 높았지만, Goal Success와 수치 계산 완료율이 낮게 나타났다.  
특히 검색된 관계식을 실제 계산으로 연결하는 단계와 불필요한 조기 종료가 주요 병목으로 확인되었다.

**쉽게 말하면**

“안전하게 틀리지 않는 것”에는 강했지만, 너무 조심해서 “할 수 있는 일도 안 하는” 문제가 컸다.

**논문 표현 예시**

> 근거 없는 응답을 억제하는 과정에서 수행 가능한 질의까지 조기 종료되는 경향이 관찰되어, 이후 버전에서는 과업 완결성을 주요 개선 목표로 설정하였다.

# V22 — Task Completion

**핵심 목표**

> **DO THE WORK THAT IS CURRENTLY POSSIBLE. ASK USER ONLY FOR TRULY MISSING INFO.**

V21.2의 과도한 보수성을 줄이고 “할 수 있는 작업은 실제로 수행”하는 데 초점을 맞춘 버전이다.

**주요 개선**

### 1. Actionability Assessment
현재 확보된 정보로 실행 가능한 작업인지 먼저 판단한다.

### 2. 직접 계산 Fast Path
합, 차이, 비율, 평균, 변화율 등은 불필요한 검색 없이 바로 계산한다.

### 3. 사용자 제공 관계식
사용자가 식과 값을 모두 제공했다면 KB 검색 없이 직접 계산한다.

### 4. Formula Execution Contract
교재 관계식 계산 전에 다음을 명확하게 확인한다.

- 계산 목표
- 원래 관계식
- 필요한 변수
- 변수의 출처
- 누락값
- 모호한 값
- 단위 적합성

### 5. Clarification Last
사용자에게 다시 질문하기 전에 기존 입력, alias, source-local 정의, derived fact를 모두 확인한다.

**개발 평가에서 확인된 특징**

Fresh real-KB 개발 과업에서 높은 수행 완료율을 보였으나, 동일 benchmark의 의미 기반 비교에서는 Goal Success와 Numerical Accuracy가 여전히 낮았다. 반면 Hallucination-free 비율은 높게 유지되었다.

**해석**

V22는 “안전성”을 유지하면서 “일을 실제로 하도록” 크게 개선했지만, 검색한 관계식을 계산 실행으로 연결하는 부분은 여전히 병목이었다.

**논문 표현 예시**

> 실행 가능성 평가와 관계식 실행 계약을 도입하여 수행 가능한 작업의 조기 종료를 줄였으며, 사용자 제공 식과 단순 계산은 검색 단계를 생략하고 직접 실행하도록 개선하였다.

# V23.1 — Remaining Failure-Class Repair (진행 예정)

> **현재 상태: 계획/수정 단계. 완료 결과가 나온 뒤 본 문서를 업데이트해야 한다.**

V23에서 남은 실패를 네 가지 일반 문제로 정리하였다.

## 1. 여러 요청을 한 번에 모두 수행

예:

```
A=34, B=61, C=29
총합과 가장 높은 항목은?
```

기존에는 총합만 계산하고 종료하는 경우가 있었다.

**개선 방법**

질문을

- 총합 계산
- 최대값 및 항목 확인

두 개의 Required Goal로 나누고, 둘 다 완료되기 전에는 종료하지 않는다.

**논문 표현**

> 복합 질의에 포함된 다수의 요구사항을 개별 목표로 분해하고 모든 필수 목표가 충족될 때까지 실행을 지속하도록 목표 관리 로직을 개선하였다.

---

## 2. 질문 맥락에 맞는 관계식 선택

문헌에 같은 출력 변수에 대한 여러 관계식이 존재하면 일반식보다 사용자가 요청한 특정 모델/암종/상황에 맞는 관계식을 우선해야 한다.

**개선 방법**

관계식 후보의 우선순위를 다음과 같이 평가한다.

1. 요청한 출력 변수
2. 질문에 명시된 모델/상황
3. 현재 사용자가 제공한 입력값
4. 실제 문헌의 literal formula
5. 추가로 요구되는 미제공 변수가 적은 공식
6. 주변 heading/paragraph 문맥

**논문 표현**

> 동일한 계산 변수를 포함하는 다수의 후보 관계식 중 질의 맥락, 입력 변수 및 주변 문헌 문맥을 고려하여 가장 적합한 관계식을 선택하도록 관계식 선택 로직을 개선하였다.

---

## 3. 검증된 원식의 안전한 대수적 재배열

예를 들어 문헌에

```
Pc = Po - Pf
```

가 있고 사용자가 `Pf`, `Pc`를 제공하며 `Po`를 요청한 경우,

```
Po = Pf + Pc
```

로 안전하게 변형하여 계산할 수 있다.

**원칙**

- 원래 관계식은 반드시 문헌에서 검증
- 목표 변수가 유일하게 풀릴 때만 수행
- 단위 호환성 확인
- 출처는 변형식이 아니라 원래 문헌 관계식을 인용

**논문 표현**

> 문헌에서 확인된 관계식을 기반으로 목표 변수를 해석적으로 재배열하여, 원식의 출처를 유지하면서 다양한 계산 요구에 대응할 수 있도록 하였다.

---

## 4. 무차원 변수 처리와 Resume

공극률, 포화도, 경험식 지수 등은 경우에 따라 단위가 필요하지 않다.

기존에는 무차원 값에도 단위를 요구하여 계산이 중단되는 문제가 있었다.

**개선 방법**

- source definition 또는 canonical role로 무차원 여부 확인
- 실제 누락 변수만 사용자에게 질문
- 후속 메시지로 값이 들어오면 기존 run 상태를 유지한 채 계산 재개
- 내부 오류명은 사용자에게 노출하지 않음

예:

```
Agent: 공극률 φ 값이 필요합니다.
User: phi=0.2
Agent: 기존 관계식과 a, m 값을 유지한 채 계산 계속
```

**논문 표현**

> 계산에 필요한 입력이 일부 누락된 경우 필요한 변수만 사용자에게 요청하고, 추가 입력이 제공되면 기존 계산 상태를 유지한 채 실행을 재개하도록 대화 상태 관리 기능을 개선하였다.

---

## 5. 검색된 문헌의 주변 문맥 확장

RAG chunk 경계 때문에 답변에 필요한 내용이 앞뒤 chunk로 분리될 수 있다.

**개선 방법**

관련성이 높은 검색 결과가 발견되면 동일 페이지 또는 인접 chunk를 제한적으로 추가 확인한다.

**논문 표현**

> 검색된 핵심 청크만으로 질의 관계를 충분히 설명하기 어려운 경우 동일 페이지 및 인접 청크를 제한적으로 확장하여 문맥 단절로 인한 정보 손실을 줄였다.

---

## 6. 복합 설명을 원자적 주장으로 나누어 검증

하나의 설명에 정의, 원인, 결과가 함께 들어가면 한 문장이 전체를 뒷받침하지 않을 수 있다.

**개선 방법**

답변을 작은 주장으로 분해한다.

```
Claim 1 → Source A
Claim 2 → Source B
Claim 3 → Source C
```

각 주장을 독립적으로 검증하고, 근거가 있는 부분은 답하며 근거가 없는 부분만 제한한다.

**논문 표현**

> 복합 설명형 질의를 복수의 원자적 주장으로 분해하고 각 주장에 대해 개별적으로 문헌 근거를 검증하여 단일 문장에서 모든 근거를 요구하는 방식의 한계를 보완하였다.

---

## 7. 검증된 관계식으로부터 제한적 수학 추론

예를 들어 검증된 관계식이

```
F = a / φ^m
```

이고 `a > 0`, `m > 0`이 문헌에서 확인된다면, φ 증가에 따라 F가 감소한다는 관계는 관계식에서 직접 도출할 수 있다.

**원칙**

- 검증된 공식만 사용
- 계수와 지수의 부호가 확인되어야 함
- 변수의 유효 범위가 명확해야 함
- 새로운 도메인 지식을 임의로 생성하지 않음

**논문 표현**

> 문헌에서 검증된 관계식에 제한적인 수학적 추론을 적용하여 변수 간 단조 증가·감소 관계 등 직접 도출 가능한 관계를 판별하도록 하였다.

# 논문에서 전체 개발 과정을 설명하는 문장

다음 문장은 시스템 개선 과정을 요약할 때 사용할 수 있다.

> 초기 시스템은 전문 문헌에 기반한 근거 검증과 안전한 응답 생성에 중점을 두었으나, 일부 수행 가능한 질의에서도 조기 종료되는 경향이 확인되었다. 이후 버전에서는 목표 지향형 실행 구조, 관계식 및 입력값 바인딩, 의미 기반 근거 검증, 복합 목표 관리, 실행 가능성 평가 및 대화 상태 유지 기능을 단계적으로 개선하였다. 최종적으로는 근거성을 유지하면서 검색, 계산 및 검증을 연속적으로 수행하고 실제 사용자 질의의 표현 다양성에 대응할 수 있는 연구지원 에이전트 구축을 목표로 하였다.
